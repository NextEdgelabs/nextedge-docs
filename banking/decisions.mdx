## Decision 1: core ownership

Should Banking own the authoritative account, deposit/loan subledger and general ledger, or orchestrate an existing bank-owned core through contracted APIs?

| Option | Result | Main dependency |
| --- | --- | --- |
| Owned core | Banking implements financial books, product economics, business-date/EOD and controlled correction | Full accounting/policy ownership, migration, reconciliation, audit and recovery acceptance |
| External-core operations platform | Banking manages approved operating/channel workflows; existing core confirms books and financial effects | Complete read/quote/instruction/status/finality contracts and bank-owned connector |
| Explicit hybrid | Name exactly which product books are owned and which are external | Cross-book settlement, source of truth, reconciliation and failure ownership for every boundary |

Recommendation for review: select the boundary for the first institution before choosing modules to build. Do not promise a core banking deployment while leaving financial book ownership undefined. If the intended product is a full new core, record Owned core explicitly and accept the corresponding scope.

Legacy permissions/holds remain facts about the old project. They are not automatically new financial grants and need not be re-asked to preserve their current behaviour. M01 acceptance is separately pending; reviewing Banking does not start M02 or accept the legacy release.
